# LINE クライアント無応答リマインド自動送信システム

コンサルティング業務向けに、クライアントごとのLINEグループを監視し、一定期間発言がなければ
自動でリマインドメッセージを送るシステムです。Google Apps Script(GAS) + Googleスプレッドシート
だけで動作し、固定費ゼロで運用できます。文言・送信間隔・支援期間などはすべてスプレッドシートの
編集だけで、非エンジニアのスタッフが変更できます。

## 1. 技術構成の比較と採用案

| 観点 | GAS + Googleスプレッドシート(採用) | Cloudflare Workers + D1 + Cron |
|---|---|---|
| 無料枠 | UrlFetch 20,000回/日、トリガー合計実行時間90分/日。今回の規模なら十分余裕 | Workers Free 10万req/日、D1 5GB。今回の規模でも十分だが枠の性質が異なる |
| 運用のしやすさ | コードはGASエディタ内で完結。スプレッドシートがDB兼設定画面なので追加UI不要 | コード管理・wranglerデプロイが必要。D1はSQLベースで別途ビューワーが要る |
| 障害時の復旧 | 実行ログがGUIで見え、エディタから即座に手動再実行できる | `wrangler tail`でのログ監視、D1はSQLクライアントでの修正が必要 |
| 非エンジニアの操作性 | ◎ スプレッドシートのセルを直接編集するだけで完結 | △ 生SQL/JSONを直接触らせるのは非現実的。別途管理画面が必要になりがち |

**採用案: GAS + Googleスプレッドシート。** 非エンジニアが直接運用できること、固定費ゼロで完結すること、
実装・保守がシンプルなことを優先しました。

## 2. 既知の技術的制約(重要)

### 2-1. X-Line-Signature の正規の署名検証はできません

LINEのWebhookは本来「リクエストヘッダー `X-Line-Signature` をチャネルシークレットでHMAC-SHA256署名し、
生ボディと比較検証する」ことが必須とされています。しかし **Google Apps ScriptのWebアプリ
(`doPost(e)`)は、Googleが2023年9月に公式に表明した仕様により、HTTPリクエストヘッダーを一切取得できません。**
そのため、GAS単体構成ではこの正規の署名検証を実装することができません。

参考:
- https://groups.google.com/g/google-apps-script-community/c/bgnzoAUV_No
- https://issuetracker.google.com/issues/67764685

このプロジェクトでは、ユーザー確認のうえ **代替の簡易認証** を採用しています。

- Webhook URLに、推測困難なランダムトークンをクエリパラメータとして付与する
  (例: `https://script.google.com/macros/s/xxxx/exec?token=xxxxxxxx`)
- `doPost` 側でこのトークンがスクリプトプロパティの値と一致する場合のみリクエストを処理する
- 一致しない場合は何も処理せず200を返す(情報漏洩・再送の誘発を避けるため)

**運用上の注意:**
- このWebhook URL(トークン込み)は"秘密情報"として扱ってください。第三者に教えたり、公開リポジトリに
  コミットしたりしないでください。
- より高いセキュリティが必要な場合は、Cloudflare Workers等の「HTTPヘッダーを読めるプラットフォーム」を
  LINEとGASの間に中継として挟み、そちらで本来のHMAC-SHA256検証を行ってからGASへ転送する構成に
  変更することを推奨します(このプロジェクトの初期質問でも代替案として提示済みです)。

### 2-2. Reply APIではなくPush APIのみを使用

リマインドは定期実行トリガー起因のため、Reply API(無料・courtesy replies)は使えず、必ずプッシュメッセージ
(課金対象)になります。「送信通数 = 送信リクエスト数 × 送信対象人数」でカウントされるため、
本システムは送信のたびにグループのメンバー数を取得し、月間の累計通数を管理します(詳細は
[8. 通数試算表](#8-通数試算表))。

## 3. 状態遷移の仕様

グループ(クライアント)ごとに以下の状態を保持します。

| フィールド | 意味 |
|---|---|
| `last_human_message_at` | 人間の最終発言時刻 |
| `last_reminder_sent_at` | ボットの最終リマインド送信時刻 |
| `reminder_stage` | 次に送るテンプレート(`A` or `B`) |
| `consecutive_reminders` | レスなしで連続送信した回数 |

**1時間ごとの定期判定:**

```
base = max(last_human_message_at, last_reminder_sent_at)
以下をすべて満たす場合のみ送信:
  - now - base >= 送信間隔(日)  (※初回はinterval_days、2通目以降はfollowup_interval_daysを使用)
  - 支援期間内(support_start <= today <= support_end)
  - enabled = TRUE
  - 送信可能時間帯内(共通設定シートで変更可)
  - 当月の送信通数が上限に達していない
```

送信後: `last_reminder_sent_at = now`, `consecutive_reminders += 1`。
次の `reminder_stage` は `consecutive_reminders == 1` なら `B`、それ以外は `A`。
結果として **A → B → A → A → A ...** と遷移します。

**Webhookで人間の発言を受信したとき:**

```
last_human_message_at = now
consecutive_reminders = 0
reminder_stage = A
```

「人間の発言」としては、**グループ内の全人間ユーザー(クライアント・自社スタッフ問わず)の発言**
をカウントします(スタンプ・画像・ファイルもテキストと同様に発言として扱います)。ボット自身の
送信は対象外です(そもそもWebhookイベントとして届きません)。

この状態遷移ロジックは `src/ReminderLogic.js` に、時刻を注入可能な純粋関数として実装されており、
`test/reminderLogic.test.js` でユニットテストしています(実行方法は[10. テストの実行方法](#10-テストの実行方法))。

## 4. セットアップ手順(非エンジニア向け)

### 4-1. LINE公式アカウント・チャネルの作成

1. [LINE Developers Console](https://developers.line.biz/console/) にアクセスし、LINEアカウントでログインします。
2. 「プロバイダー」を新規作成(または既存のものを選択)します。
3. プロバイダー内で「新規チャネル作成」→「Messaging API」を選択し、必要事項を入力してチャネルを作成します。
4. 作成したチャネルの **「Messaging API設定」タブ** を開きます。

### 4-2. LINE側の必須設定

「Messaging API設定」タブと「応答設定」タブで、以下のように設定してください(依頼の前提条件通りです)。

| 設定項目 | 値 | 場所 |
|---|---|---|
| 応答モード | Bot | 「応答設定」タブ |
| Webhookの利用 | ON | 「Messaging API設定」タブ |
| 応答メッセージ | OFF | 「応答設定」タブ |
| あいさつメッセージ | OFF | 「応答設定」タブ |
| グループ・複数人トークへの参加を許可 | ON | 「Messaging API設定」タブ下部 |

「Messaging API設定」タブの一番下にある **チャネルアクセストークン(長期)** の「発行」ボタンを押し、
表示されたトークンをコピーしておきます(後の手順4-5で使います)。

### 4-3. スプレッドシート側の準備

1. 新しいGoogleスプレッドシートを作成します。
2. メニュー「拡張機能」→「Apps Script」を開きます。
3. 開いたApps Scriptエディタに、このリポジトリの `src/` 以下の各 `.js` ファイルの中身を、
   同名のスクリプトファイルとしてそれぞれコピー&ペーストします(`appsscript.json` はエディタの
   「プロジェクトの設定」→「"appsscript.json" マニフェスト ファイルをエディタで表示する」に
   チェックを入れると編集できます)。
   - エンジニアが作業する場合は、`clasp` を使うと効率的です。`.clasp.json.example` を
     `.clasp.json` にコピーし、`clasp create` または `clasp clone` でスクリプトIDを設定した上で
     `clasp push` してください。
4. スプレッドシートに戻り、いったんページを再読み込みします。「リマインドBot管理」という
   カスタムメニューが表示されます(表示されない場合は再度リロードしてください)。

### 4-4. 初期セットアップの実行

1. 「リマインドBot管理」メニュー → **「① 初期セットアップ(シート作成)」** を実行します。
   - 初回はGoogleから権限承認を求められるので、内容を確認して許可してください。
   - 「クライアント設定」「メッセージ文言」「共通設定」「送信ログ」の4シートが自動作成されます。
2. 「② LINEチャネルアクセストークンを設定」を実行し、手順4-2でコピーしたトークンを貼り付けます。

### 4-5. Webアプリとしてデプロイ

1. Apps Scriptエディタ右上の「デプロイ」→「新しいデプロイ」を開きます。
2. 種類の選択で歯車アイコンから「ウェブアプリ」を選びます。
3. 「アクセスできるユーザー」は **「全員」** を選択します(LINEプラットフォームからの匿名アクセスを
   受け付ける必要があるためです)。
4. 「デプロイ」をクリックし、表示されるウェブアプリのURLを控えます。

### 4-6. Webhook URLをLINEに設定

1. スプレッドシートの「リマインドBot管理」メニュー → **「③ Webhook URLを表示」** を実行します。
2. 表示された `https://script.google.com/macros/s/xxxx/exec?token=xxxxxxxx` の形式のURLを
   コピーします。
3. LINE Developers Console の「Messaging API設定」タブ → 「Webhook URL」欄に貼り付け、「更新」します。
4. 「検証」ボタンを押し、成功(Success)と表示されることを確認します。

### 4-7. 定期実行トリガーの設定

「リマインドBot管理」メニュー → **「④ 1時間ごとの定期実行を設定」** を実行します。これで1時間おきに
自動判定が走るようになります。

### 4-8. 動作確認

1. LINE公式アカウントを、テスト用のLINEグループに招待します。
2. 「クライアント設定」シートに、その招待したグループの行が自動追加されていることを確認します
   (`memo`列に「自動追加」と表示されます)。
3. その行の `client_name` を入力し、`support_start`・`support_end`(日付)を設定し、`enabled` を
   `TRUE` にします。
4. 「今すぐ判定を実行(テスト用)」メニューを実行し、「送信ログ」シートに結果が記録されることを
   確認します(送信可能時間帯外などの理由で送信されないこともあります。その場合はログではなく
   何も記録されません。強制的にテストしたい場合は共通設定シートの時間帯を一時的に広げてください)。

## 5. スプレッドシートの構成

### シート1「クライアント設定」

| 列名 | 意味 | 変更可否 |
|---|---|---|
| `client_name` | クライアント表示名。メッセージ本文の `{client_name}` に差し込まれる | スタッフが編集可 |
| `group_id` | LINEグループのID。join時に自動入力される | 基本的に編集不要 |
| `enabled` | `TRUE`でこのクライアントへのリマインドを有効化 | スタッフが編集可 |
| `support_start` | 支援開始日(この日より前は送信しない) | スタッフが編集可 |
| `support_end` | 支援終了日(この日より後は送信しない) | スタッフが編集可 |
| `interval_days` | 最終発言から1通目のリマインドを送るまでの日数 | スタッフが編集可 |
| `followup_interval_days` | 2通目以降のリマインド間隔(日数) | スタッフが編集可 |
| `template_A_key` | Aパターンで使う「メッセージ文言」シートのkey | スタッフが編集可 |
| `template_B_key` | Bパターンで使う「メッセージ文言」シートのkey | スタッフが編集可 |
| `last_human_message_at` | 人間の最終発言時刻(自動更新) | 編集不要(緊急時のみ手動修正可) |
| `last_reminder_sent_at` | ボットの最終送信時刻(自動更新) | 編集不要 |
| `reminder_stage` | 次に送るテンプレート `A`/`B`(自動更新) | 編集不要 |
| `consecutive_reminders` | 連続送信回数(自動更新) | 編集不要 |
| `memo` | 自由記入欄 | スタッフが自由に使ってよい |

### シート2「メッセージ文言」

| 列名 | 意味 |
|---|---|
| `key` | テンプレートの識別子(クライアント設定シートの `template_A_key` 等から参照される) |
| `本文` | メッセージ本文。`{client_name}` と書くとクライアント名に自動置換される |

### シート3「共通設定」(縦持ちのキー・値表)

| 設定項目 | 意味 | デフォルト |
|---|---|---|
| 送信可能開始時刻 | この時刻以降のみ送信(例: `10:00`) | 10:00 |
| 送信可能終了時刻 | この時刻より前のみ送信(例: `18:00`) | 18:00 |
| 曜日除外 | 送信しない曜日をカンマ区切りで(例: `土,日`) | 土,日 |
| 祝日除外 | `TRUE`でGoogleカレンダーの日本の祝日を送信対象外にする | TRUE |
| 月間送信上限 | この通数を超える見込みなら送信を停止する | 180 |
| 管理者通知先メールアドレス | 上限超過・送信失敗時の警告メール送信先 | (空、要設定) |

### シート4「送信ログ」(自動追記・閲覧専用)

| 列名 | 意味 |
|---|---|
| 日時 | 判定/送信を行った日時 |
| client | クライアント名 |
| group_id | LINEグループID |
| テンプレkey | 送信したテンプレートのkey |
| 通数 | 今回の送信で消費した通数(=送信時点のグループメンバー数) |
| 結果 | `成功` / `失敗` |
| エラー内容 | 失敗時のエラーメッセージ |

## 6. クライアントのグループを追加する手順

1. LINE公式アカウントを、対象クライアントとのLINEグループ(またはLINE複数人トーク)に招待します。
2. 招待されると自動的に「クライアント設定」シートに新しい行が追記されます(`group_id` が自動入力され、
   `enabled` はデフォルトで `FALSE`、`memo` に「自動追加」と表示されます)。
3. その行を開き、`client_name` / `support_start` / `support_end` / `interval_days` /
   `followup_interval_days` / `template_A_key` / `template_B_key` を必要に応じて編集し、最後に
   `enabled` を `TRUE` にします。
4. ボットがグループから退出させられた場合は、自動的に `enabled` が `FALSE` に戻されます(誤送信防止)。

手動でIDをコピペする必要は一切ありません。

## 7. 日常運用でよく変更する項目

- **文言を変えたい** → 「メッセージ文言」シートの該当する `key` の行の「本文」列を編集するだけです。
- **リマインドの間隔を変えたい** → 「クライアント設定」シートの該当行の `interval_days` /
  `followup_interval_days` を編集します。
- **支援期間を延長・終了したい** → `support_start` / `support_end` を編集します。
- **一時的に止めたい** → `enabled` を `FALSE` にします。
- **送信可能時間帯・曜日を変えたい** → 「共通設定」シートを編集します。
- **月間上限を変えたい** → 「共通設定」シートの「月間送信上限」を編集します(無料プランの上限は
  月200通のため、それを超えない値にしてください)。

いずれもコードを触る必要はありません。

## 8. 通数試算表

無料プラン(コミュニケーションプラン)の上限は **月200通** です。本システムはデフォルトで
安全マージンを見て **月180通** で送信を停止します。1回の送信あたりの通数は「そのグループの
メンバー数」分カウントされます。

`月間消費通数 ≒ クライアント数 × 平均グループ人数 × クライアント1件あたりの月間リマインド回数`

リマインド回数は「クライアントがどれだけ応答するか」に依存します。目安として3パターン試算します
(`interval_days=3`, `followup_interval_days=2` のデフォルト設定、30日/月で計算)。

| シナリオ | 平均グループ人数 | クライアント1件・月間リマインド回数(目安) | 1クライアントあたり月間消費通数 | 月180通で運用できるクライアント数目安 |
|---|---|---|---|---|
| 標準(数回のリマインドで応答がある) | 3人 | 4回 | 12通 | 約15件 |
| やや応答が遅い | 3人 | 8回 | 24通 | 約7件 |
| 最悪ケース(1ヶ月まったく応答なし) | 3人 | 14回 (`(30-3)/2+1`) | 42通 | 約4件 |
| 少人数グループ・標準 | 2人 | 4回 | 8通 | 約22件 |

**読み方:** 実際の運用ではクライアントが途中で応答すれば `reminder_stage` が `A` にリセットされ
消費通数は減ります。継続的に多数のクライアント(10件超)を無料プランのみで運用する場合は、
送信間隔を広げる・送信可能時間帯や曜日除外を活用する・グループの人数を絞る、といった工夫で
通数を抑えることを推奨します。上限に近づくと自動的に送信が止まり管理者にメール通知されるため、
使いすぎて誤って課金プランに切り替わる心配はありません(ただし送信が止まったクライアントには
リマインドが届かなくなる点に注意してください)。

## 9. トラブルシューティング

| 症状 | 確認・対処 |
|---|---|
| Webhookの「検証」が失敗する | Webhook URLに `?token=...` が正しく含まれているか確認。「③ Webhook URLを表示」で再取得して貼り直す |
| グループに招待してもシートに行が追加されない | LINE Developers Consoleで「グループ・複数人トークへの参加を許可」がONか確認。デプロイが「全員アクセス可」になっているか確認 |
| リマインドが送信されない | 「共通設定」シートの送信可能時間帯・曜日除外・祝日除外、対象クライアント行の `enabled`/`support_start`/`support_end` を確認。「送信ログ」シートに記録がなければ、そもそも送信対象外の可能性が高い |
| 送信ログに「失敗」が記録される | エラー内容列を確認。チャネルアクセストークンの期限切れ・入力ミスが多い原因。「② LINEチャネルアクセストークンを設定」で再設定する |
| 月間送信上限に達した旨のメールが届く | 「共通設定」シートの月間送信上限、または各クライアントの送信間隔を見直す。翌月になれば自動的にリセットされる(送信ログの月次集計のため) |
| 管理者通知メールが届かない | 「共通設定」シートの「管理者通知先メールアドレス」が正しく入力されているか確認 |
| 二重送信が発生した | LockServiceにより通常は発生しない設計だが、発生した場合は「送信ログ」シートで日時・group_idを確認し、Apps Scriptの「トリガー」画面で重複したトリガーが登録されていないか確認する |

## 10. テストの実行方法

状態遷移ロジック(`src/ReminderLogic.js`)は、GASに依存しない純粋関数として実装されており、
Node.js上でJestを使ってユニットテストできます。

```bash
npm install
```
